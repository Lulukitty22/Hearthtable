- **Testing** (2026-10-21 at 4:00 am PDT): unit tests, emulator tests, Rules tests from Milestone 4, and one browser end-to-end test from Milestone 2. See [Testing strategy](#testing-strategy).

## Hosting: browser plus Firebase

Every trusted need in the current documentation can be met without server code:

| Need | Pure browser + Firebase method |
|---|---|
| Resource holds and one-time resolution | Firestore client `runTransaction`. The request document id is the stable action identity. The transaction refuses if the action status is not `pending`, which makes duplicate approval a no-op. Usable amount → hold → consumed or returned happens in the same transaction. |
| Who may write | Security Rules check authority (below). A player's submission may write the request and its hold to the character, because the hold is part of the selected workflow. Ordinary sheet edits in a campaign go through DM approval, and Rules refuse submissions from a revoked delegate. |
| DM-only approval and membership | Rules check `/campaigns/{campaignId}/members/{uid}.role`. |
| Character tab and line privacy | Screen-only: viewers' browsers receive the data and the app hides it. Rules do not block those reads. Owned by [Campaigns and Shared Data](../Systems/Campaigns%20and%20Shared%20Data.md#character-sheet-visibility). |
| Accounts: Alias, approval and site administrators | One `/accounts` area. `/accounts/{uid}` holds the Alias, approval status and administrator flag, and no Google email or profile data in anything publicly readable. Rules stop a user from changing their own approval or administrator fields. Admins approve accounts in the user interface; no Admin SDK or custom claims are needed. Firestore cannot enforce a unique value across documents, so a small Alias index (`/accounts-by-alias/{normalizedAlias}`) is written in the same batch and checked with `existsAfter`. The same pattern covers unique campaign and character paths. Alias rules are owned by [Campaigns and Shared Data](../Systems/Campaigns%20and%20Shared%20Data.md#guest-viewing-and-accounts). |
| Game calculations | The shared TypeScript engine runs in the browser. The DM's browser resolves approved actions, using the same code a server would run later. |
| Live updates | Native Firestore listeners, as selected in [Campaigns and Shared Data](../Systems/Campaigns%20and%20Shared%20Data.md#planning-scale-and-cost-model). |

What will eventually need compute (all deferred):

- **Discord bot:** an HTTP-interactions endpoint, or a Gateway client.
- **LLM helpers:** an API key cannot ship in the browser bundle.

Options for that compute, in order of preference:

1. **Cloud Functions or Cloud Run.** Both have free allowances on Blaze.
2. **The user's PC.** Acceptable for the bot, per the existing documentation.
3. **A GCP e2-micro always-free VM**, if a persistent Gateway bot is wanted or Cloud Run work should move onto it.

**Blaze is needed** only once the app moves to real Firebase, and then for portrait Cloud Storage. The budget direction (target no-cost allowances, Blaze acceptable) is owned by [Campaigns and Shared Data](../Systems/Campaigns%20and%20Shared%20Data.md#hosted-backend-comparison).

**A small server of our own, if ever wanted.** Nothing planned needs one: Firestore listeners deliver live updates straight to browsers, whichever host serves the files. As a check, a generous workload (33 connected viewers, 1,000 updates/day of about 1 KB to every viewer, plus a Discord bot) fits free on either:

- A Cloudflare Durable Object uses about 110 of its 100,000 free daily requests (incoming WebSocket messages count 20:1; outgoing messages are free), and even awake all day stays under its 13,000 GB-seconds/day.
- Google's free e2-micro VM (0.25 vCPU sustained, 1 GB RAM, always on) handles it easily; data sent out would be about 1 GB/month only if everyone were connected every day. The user expects far less, since the group does not play daily.
- Cloud Run and Cloud Functions suit short requests such as bot commands, not streams held open all day.
- An always-connected Discord bot needs the VM; a bot that receives Discord's HTTP calls fits Cloud Functions or Workers.

## Security Rules scope

Rules check who may read and write: campaign membership, the DM role, delegation and its revocation, DM approval for character changes, the account approval and administrator fields, and site-administrator read access. They do not check whether a hold amount or a calculation is correct, and they do not hide private content: all privacy (campaigns, characters, tabs, lines, DM-only notes) is screen-only ([Character-sheet visibility](../Systems/Campaigns%20and%20Shared%20Data.md#character-sheet-visibility)).

## Local development on the emulator

- **Everything runs on the user's PC through the Firebase Emulator Suite** (Auth, Firestore, Storage, Hosting). No real Firebase project exists yet; `firebase.json` and `firestore.rules` are emulator-only for now.
- The app must not depend on anything running locally except the emulator, so it can move to real Firebase with only a connection-configuration change.
- Friends can reach a PC-hosted session only while the PC is on, through a tunnel or port forwarding. This is for testing only.

**First site administrator.** Rules stop users from setting their own administrator flag, so the first administrator must be set outside the app. On the emulator, seed data sets it. On real Firebase it is open (see above).

**Exported files and sign-in.** Firebase Authentication will not run from a downloaded file's `file://` origin, while guest reads of public data can. Built in S10 (2026-10-24 at 3:15 pm PDT (America/Los_Angeles)): the downloaded file therefore only frames the app's sheet-only page for the character (`…/<character>/Export`), so the sheet runs at the app's own address. Verified by a browser test: the file opens from disk, shows the current sheet, follows later saves and says when the character is gone. A signed-in viewer inside the frame may appear as a guest, because browsers keep a framed page's storage apart; that matters only once privacy arrives. The hosted app must allow framing and be reachable; on real Firebase this is checked in Milestone 7. The export requirement is owned by [Campaigns and Shared Data](../Systems/Campaigns%20and%20Shared%20Data.md#html-and-live-state-requirements).

## Stack

- pnpm workspaces, TypeScript in strict mode.
- Vite + React for the web app.
- Vitest for unit and emulator tests; Firebase's rules-testing library for Rules tests; Playwright for browser end-to-end tests.
- ESLint + Prettier.
- Firebase JavaScript SDK (Auth, Firestore, Storage) only inside the storage and web packages. The engine never imports Firebase.

Decisions made while scaffolding:

- Packages use the `@hearthtable/` prefix, and packages export their TypeScript sources directly; there is no separate build step for libraries (user decision for the prefix).
- The emulator project ID is `demo-hearthtable`. The `demo-` prefix means Firebase treats it as offline-only, so nothing can reach a real project (user decision).
- TypeScript is pinned to 6.0, because the ESLint TypeScript plugin does not yet support TypeScript 7.
- Install scripts for `@firebase/util`, `protobufjs` and `re2` are turned off in `pnpm-workspace.yaml`; none is needed for this app.
- `firestore.rules` began by allowing anyone to read and write the `records` collection, for the emulator only; `storage.rules` denied everything until S11 (2026-10-24 at 4:02 pm PDT (America/Los_Angeles)), when it began allowing portraits at `portraits/<character path>/<file>`: readable by anyone, uploaded by someone who may edit that character (its owner by Alias, or a DM of its campaign, checked against Firestore), PNG, JPEG, WebP or GIF up to 2 MB. Real Rules come in Milestone 4, and nothing may be deployed before then. Since Milestone 4 S1 (2026-10-23 at 6:14 am PDT (America/Los_Angeles)), they also cover `/accounts` and the Alias index (see the S1 note under Repository layout). Since S3 (2026-10-24 at 5:03 am PDT (America/Los_Angeles)), anyone may read records, but only an approved account may write them: the owner of an `account/<Alias>/…` record, matched through the Alias index, or a DM of the campaign for `campaign/<name>/…` records (listed in the campaign's `dms`, below). The scope and owner are read from the document id, and a save's `path` field must name the same ones. Core records are written only by seeding. Since S5 (2026-10-24 at 5:40 am PDT (America/Los_Angeles)), a campaign is `/campaigns/{id}` (`name`, `dms`, `players`, `createdAt`; the id is the name's path segment in lower case, so names differing only in capitals cannot both exist), readable by anyone. An approved account creates one with itself as the only DM; DMs change the lists; a member may remove only themselves; a site administrator may restore DM; every change keeps at least one DM. Join requests are `/campaigns/{id}/requests/{uid}`, created by an approved non-member with the current code and readable by that person and the DMs. The current code is `/campaigns/{id}/private/invite` (DMs only), and `/invites/{code}` names the campaign a code joins: anyone signed in may look up a code, but codes cannot be listed. Rules let DMs add players directly; the app adds them only from join requests. Since S6 (2026-10-24 at 6:16 am PDT (America/Los_Angeles)): `/campaigns/{id}/insertions/{auto}` (`by`, `name`, `path`, `records`, `at`) is created by an approved member for a path under their own Alias in that campaign and read or deleted by them and the DMs; the DM's approval writes the records through the record Rule. `/campaigns/{id}/control/{record document id}` (`delegates`) is readable by anyone and written by the character's owner (by the Alias in its path), naming only members. Since S7 (2026-10-24 at 6:38 am PDT (America/Los_Angeles)): `/campaigns/{id}/proposals/{auto}` (`kind`, `by`, `target`, `control`, `note`, `writes`, `deletes`, `at`) is the DM review queue; an `edit` of a campaign character comes from its owner or a current delegate (checked against the character's control document, so a revoked delegate is refused), `delete` and `replace` only from the owner, and an `entry` from any member outside Characters; the author and the DMs read and delete it. Seeding and the storage contract tests use the emulator's `owner` token, which switches Rules off.
- Emulator data persists between runs, and seeding skips existing records (user decisions, 2026-10-22 at 1:52 pm PDT (America/Los_Angeles)).

## Repository layout

- `packages/kernel`: record envelope, module registry, resolved-state pipeline, grants, dice, validation results and the transition interface. Systems read their record data through Zod schemas (`readField`, `readDefinition`) that report problems instead of guessing.
- `packages/systems/*`: one folder per system. Milestone 2 needs:
  - `abilities`, `proficiency`, `skills-and-saves` (including expertise and initiative), `features` (feats and class features as modifier sources, such as Alert, War Caster and Skill Expert)
  - `hit-points`, `armor-class`, `active-effects` (a minimal store of which effects are active, so AC shows Mage Armor or Shield only when active; no clock or expiry yet)
  - `resources` (limited-use pools with reset types: Arcane Recovery, Tinker's Magic, the free Magic Initiate cast, Heroic Inspiration)
  - `spellcasting`, `spellbook-readiness`
  - `containers`, `attunement` (including held state for conditional bonuses such as the Wand)
  - `magazines` (chambers and charge display only)
- `packages/games/dnd5e-2024`: the game module, including class records and each class's own slot table (Vanilla+ adds slots per class; see [Character Creation and Advancement](../Systems/Character%20Creation%20and%20Advancement.md)).
- `packages/rulesets/hearthtable-vanilla-plus`: the ruleset data.
- `packages/play` (Milestone 5 S2, 2026-10-24 at 10:41 pm PDT (America/Los_Angeles)): the pure rules of play in a campaign, apart from any one character: the game clock (seconds since midnight before Day 1, read as "Day 3, 2:32 pm"; six seconds a round) and scene names and folders. Since S3 (2026-10-25 at 12:24 am PDT (America/Los_Angeles)) it also holds the turn order (initiative, ties by entry time, the DM's kept order with latecomers placed by initiative), passing turns and rounds, the encounter clock, initiative rolls, the action budget and NPC instance names; since S4 (2026-10-25 at 1:11 am PDT (America/Los_Angeles)) also game moments (`moments.ts`: clock plus steps of 1/40 s, durations read from spell text, time left); since S5 (2026-10-25 at 1:53 am PDT (America/Los_Angeles)) downtime activities (`activities.ts`: the activity-type registry and running time; `activityTypes.ts`: Short Rest, Long Rest and the note as modules); since S6 (2026-10-25 at 2:23 am PDT (America/Los_Angeles)) requests (`requests.ts`: request kinds as modules, holds, eligibility).
- `packages/engine`: the composition root. It lists the modules and resolves a character's records under a ruleset; views, tests and scripts use it.
- `packages/storage`: the `Repository` interface plus `memory` and `firestore` adapters. Saves are all or nothing, and a save edited from an older revision is refused as a conflict rather than applied. `deleteAll` deletes several records together (such as a character with its tabs and history) on the same terms, in one transaction of at most 500 records. `watchUnder` (S9, 2026-10-24 at 3:07 pm PDT (America/Los_Angeles)) reports a record and everything under it now and after every saved change; the Firestore adapter combines its two listeners' reports, since one save can reach them separately. The Firestore adapter's Milestone 2 mapping (one `records` document per record, its id the encoded path, with `ancestors` for listing a sheet's tabs) is provisional until the Milestone 4 schema; Firestore cannot store a list inside a list, so data never uses one. `accounts.ts` (2026-10-23 at 6:14 am PDT (America/Los_Angeles), Milestone 4 S1) owns the Alias format check, the normalized form used for uniqueness (lower case, `-` read as `_`) and `claimAlias`, which creates `/accounts/{uid}` (`alias`, `status` pending, `admin` false, `createdAt`) and `/accounts-by-alias/{normalized}` (`uid`, `alias`) in one transaction. Both are readable by anyone; Rules allow only that paired creation by the signed-in owner. Since S2 (2026-10-24 at 4:06 am PDT (America/Los_Angeles)), a site administrator may approve a pending account (`approveAccount`: status to approved, with `approvedBy` and `approvedAt`), which is the only update Rules allow; nobody deletes an account. `watchPendingAccounts` lists the accounts waiting.
- `packages/storage/src/table.ts` (Milestone 5 S2, 2026-10-24 at 10:41 pm PDT (America/Los_Angeles)): a campaign's game in progress. `/campaigns/{id}/play/state` holds the clock and the current scene's record path (DMs write it; never deleted); `/campaigns/{id}/log/{entry}` is the campaign log, only ever added to: members post text (`post`), DMs also record what happens (`scene`, `clock`, `title`). Scenes are records (`campaign/<C>/Encounters/…`, `campaign/<C>/Downtime/…`, kinds `encounter` and `downtime`) so NPC instances sit under them; sheets leave scenes out of the definitions they load. `openTable` starts a campaign's first downtime scene when a DM first opens the DM's view. Log entries written together carry `n`, their order within the write. `encounters.ts` (S3, 2026-10-25 at 12:24 am PDT (America/Los_Angeles)): `/campaigns/{id}/encounters/{scene name}` holds an encounter's turn state (scene, start clock, participants, surprised, round with 0 for initiative, current, the order kept since round 1, `seq` counting turn changes, and when each participant's latest turn began); DMs write it, and whoever controls the current participant may only pass the turn on. Its `participants/{encoded path}` documents hold each participant's initiative and budget ticks, written by the controller (owner Alias or delegate) or a DM. Starting an encounter ends the downtime scene, deploys NPC instances as record copies of their templates under the scene, and rolls their initiative; ending one writes the final order to its record, which Rules then keep read-only with everything under it, and starts downtime. The engine reads typed-in values from a character record's `authored` map (`authoredFrom`), so a quick NPC template needs no class levels. S4 (2026-10-25 at 1:11 am PDT (America/Los_Angeles)): the encounter document also counts `step`, which any member moves on by one per action or reaction; `effects.ts` (`endEffects`) clears ended effects from a character and logs each ending once under a fixed log id (`ended-<effect id>`). S5 (2026-10-25 at 1:53 am PDT (America/Los_Angeles)): `packages/systems/conditions` (conditions from definitions and character entries, Exhaustion levels, going down; grants while applied) and the `d20-tests` bonus target; `hit-points.dice` tracks spent Hit Point Dice; `activities.ts` stores downtime activities (`/campaigns/{id}/activities`), `conditions.ts` applies conditions with a log entry, and `passTime` ends a downtime scene into a new one. S6 (2026-10-25 at 2:23 am PDT (America/Los_Angeles)): `actions.ts` stores requests (`/campaigns/{id}/actions`, queued with their holds, revised in place, cancelled or rejected once); the kernel's `heldAmounts` reads an unstored `holds` record that spell slots, resource pools and inventory lines subtract (`apps/web/src/play/actions.ts`). The web app passes the campaign's current moment to sheet and table resolution as an unstored `game-time` record (`apps/web/src/play/gameTime.ts`).
- `apps/web`: the React sheet viewer and editor. Each system lists the tabs it provides (`provides.uiTabs`), and the app shows the tabs of enabled modules; a declared tab the app cannot draw shows as unavailable. Pages follow record paths ([web addresses](../Systems/Campaigns%20and%20Shared%20Data.md#account-organization-and-address-design), 2026-10-24 at 3:54 am PDT (America/Los_Angeles)): `/` lists characters, `/Campaigns/Riverbed_of_Strings/Characters/VR_Lulu/Carol_Elfnein` opens Carol (in her campaign since 2026-10-24 at 6:16 am PDT (America/Los_Angeles)), and a last segment `Edit` or `DM` names the view. A character's address shows the sheet read-only, with an Edit button for whoever may edit it, and its `/Edit` address is the editor; anyone else who opens `/Edit` sees the sheet read-only with a note (2026-10-24 at 4:52 am PDT (America/Los_Angeles)). Until campaigns add DMs and delegates, only the approved owner of an account record may edit it (`apps/web/src/account/permissions.ts`); site administrators are not given edit rights. On the read-only sheet, inputs show as plain values, edit buttons are hidden and nothing can be dragged (`Draggable` in `Grid.tsx`, `canEdit` on every tab). Security Rules enforce the same since S3. Since S4 (2026-10-24 at 5:24 am PDT (America/Los_Angeles)), an account record's address opens what is stored there: `/Accounts/<Alias>` is the account's home, a folder (a `folder` record, or a path with entries below it) lists its entries, a character opens its sheet, and a custom item, spell or feature opens a page with its name and description (`apps/web/src/home`). The approved owner gets New (folder, character, item, spell, feature), Copy as (new name and destination folder; a 1:1 copy of the entry and everything under it) and Delete (a folder with entries asks for its name to be typed); names follow `home/names.ts`, which refuses duplicates and the address words listed in `routes.ts`. A sheet now reads definitions from its owner's whole account, leaving out other characters.
